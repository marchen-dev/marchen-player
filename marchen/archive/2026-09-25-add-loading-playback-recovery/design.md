## 背景

完整加载由 `packages/player-loading/src/service.ts` 的 `executeFullLoad` 编排，`pipelines/load.ts` 提供匹配和弹幕等分段函数。当前 `skipDanmaku` 只在 `waiting_user` 生效，匹配异常进入不保留视频的通用 `error`；首次弹幕请求异常降级为空列表，重新匹配异常也进入通用 `error`。

`use-native-player-runtime.ts` 仅在 `ready/reloading` 激活播放运行时，因此播放期间的弹幕恢复必须保持这两个状态及相同视频对象/媒体身份。工作区的匹配结果展示已改为 `MatchResultToast`、`MatchInfo` 和 `getMatchInfo`，本变更接续这份实现，不恢复顶部标题，也不覆盖字幕等其他未提交改动。

## 目标与非目标

**目标：**

- 保留默认加载顺序，为网络等待与失败提供直接播放和分阶段重试。
- 播放期间更新弹幕不销毁媒体会话，失败保留原数据。
- 显式终止被跳过的在线操作，隔离切集、取消、重复点击和迟到结果。
- 保留本地弹幕、有效旧弹幕及匹配元数据，确保直接播放仍可保存可恢复的历史来源。
- Electron/Web 桌面和全屏交互一致。

**非目标：**

- 不改成导入后立即播放并后台自动匹配，不自动回放或补发过去的弹幕。
- 不修改媒体解码策略、上游 API、数据库版本或移动端布局。
- 不重构所有通用请求错误提示；仅处理本流程取消/失效请求所产生的误提示。

## 决策

### 1. 增加有上下文的匹配失败和恢复状态

在现有 discriminated union 中增加匹配可恢复失败态，携带完整 `VideoInfo`、失败阶段和可展示错误；通用 `error` 保留给无法继续的导入等错误。匹配重试直接复用导入结果，成功后回到原有弹幕流程，无准确结果进入手动选择。

`ready/reloading` 中区分在线弹幕成功、主动跳过、请求失败及恢复操作失败。使用结构化字段或判别联合表达，不依靠空数组推断失败；保留或兼容现有 `danmakuLoadFailed` 展示契约，避免两套状态分歧。请求失败和零条结果的判定来自请求结果。播放期间重试失败回到携带原快照的 `ready` 并附操作错误，不进入通用 `error`。

```text
导入 → matching → loading_danmaku → ready
          │               │          │
          │失败           │失败      ├─ 主动重试 → reloading
          ▼               └→ ready   │                 │
   可恢复匹配失败                     └──── 成功或失败 ──┘
     ├─ 重试 → matching
     ├─ 手动选择 → waiting_user → loading_danmaku
     └─ 直接播放 → ready

matching / loading_danmaku / waiting_user → 直接播放 → ready
```

### 2. 直接播放是当前在线操作的终止分支

扩展跳过命令的适用阶段，在视频导入完整之后、在线匹配或弹幕等待及匹配失败时均可执行。命令同步使原在线操作失效，之后用当前视频、已确认匹配和已有可用弹幕形成 `ready`。保持媒体准备流程，自然支持浏览器的自动播放限制，不承诺文件不可解码时仍能播放。

保留本地弹幕；在线缓存仅在能确认属于当前已确认匹配时使用，无匹配时不得将未知旧在线弹幕绑定到当前视频。缓存或历史读取失败不能使直接播放永远不可用，应退化到已有内存数据或空弹幕，并保留独立诊断。

直接播放后不自动恢复在线操作。已有匹配但跳过弹幕时，在设置提供主动加载/重试入口；未匹配时复用“匹配动漫”的手动入口。正常未跳过路径不提前启动视频，因此不引入前 0、1 秒弹幕因网络等待而错过的问题。

### 3. 恢复命令按失败阶段执行

- 加载页“重试匹配”仅重新执行匹配及后续必要步骤，不再导入文件或计算 hash。
- “重试弹幕”使用已确认的剧集，强制在线刷新，不重新匹配，不重新创建视频来源。
- 播放中“重新匹配”沿用人工选择；选中新剧集后请求新弹幕，成功时一起提交新匹配和弹幕。失败保留原匹配及弹幕，并记录待重试目标；重试再次请求该目标，避免错误地重试原剧集。
- `reloading` 保存原可播放快照、操作类型和目标。请求期间原弹幕继续工作，成功后由现有弹幕运行时按当前时钟更新；不能改变播放位置、暂停状态或媒体身份。
- 恢复操作使用 `exhaustMap` 或等效互斥，UI 禁用对应重复操作，失败后恢复可点击。

### 4. 请求生命周期覆盖状态与副作用

优先使用 RxJS 切换/终止操作符编排加载和恢复分支，为每次媒体加载及在线操作分配代次。新视频、取消和直接播放立即使旧代次失效，旧事件必须在 reducer/提交边界被拒绝。

仅取消订阅不能停止 `defer(async ...)` 中已经启动的 Promise，尤其无法阻止其后续缓存/历史写入。实现需把在线请求结果与持久化提交分离，检查有效代次后才进入提交；通过同一视频 hash 的顺序提交及有效性复查防止较旧写入覆盖较新数据。已经发起的本地写入不可假定可取消，要确保后续有效提交顺序以及错误不会回写旧 UI。

API adapter/请求层可传递 `AbortSignal` 时取消实际请求，并在每个 await 后、任何状态/提示/写入之前检查有效性。Abort 或已失效操作不能发出通用错误 Toast；若传输不能取消，结果必须静默丢弃。新 load/cancel 同时终止 full-load 与 rematch/retry 分支。对同 hash 重新打开也依赖代次判断，不能只比较 hash。

### 5. 保留已有数据与历史记录

首次在线弹幕失败优先保留当前有效弹幕或同匹配缓存、本地弹幕，不再无条件用空列表覆盖历史。只有成功返回的弹幕结果才替换对应在线来源，本地来源及用户选择保持现有约定。

跳过时保存完整的 `getPersistentMediaSource(video)`、hash 及已确认匹配；没有匹配时沿用当前未匹配表示和文件名。禁止将 Web File/blob URL 存入历史。历史/缓存写入错误单独处理，不误报为上游匹配失败、不终止本来可播放的媒体；这仅覆盖本次加载和恢复的持久化边界，不扩展为全库重构。

### 6. UI 复用现有区域

- `PlayerProvider` / `Timeline`：匹配与弹幕等待的步骤说明下方放次要“直接播放”按钮，不加按钮下方说明文案。匹配失败时在同一区域显示原因，直接播放作为主按钮，旁边为重试匹配，另有手动匹配入口。
- `MatchAnimeDialog`：底部现有“不加载弹幕”改为“直接播放”。区分完成选择/跳过与用户取消关闭，避免 `onClosed` 把刚开始的播放取消。
- `MatchResultToast`：播放器内失败提示附“重试弹幕”动作。恢复失败不误提示“已更新匹配”，取消/跳过不弹错误。
- `MatchInfo`：提供持续可见的状态与恢复入口，Toast 消失后仍可重试；未匹配保留手动匹配，失败操作使用相应目标和状态文案。
- 保持 Toast 在全屏元素内，按钮可键盘操作，错误可被辅助技术感知，遵循仓库默认箭头指针规则。

## 风险与权衡

- 网络完成与直接播放可能在同一事件循环相邻发生：以先接受的有效状态转换为准；已 ready 的旧按钮点击不得再次加载，跳过先接受后必须拒绝网络结果。
- RxJS 退订和传输取消不等同于撤销持久化；代次检查与提交顺序需要可控延迟测试覆盖，包含同 hash 重新打开。
- 缓存按 hash 存储，不能凭存在缓存就认定与新剧集一致。重新匹配失败保留原快照，成功才替换。
- 现有弹幕热更新是否在当前时间接入，以及是否意外重建播放会话，需要真实播放器证据，不能只靠状态机测试证明。
- 并行工作区仍有匹配提示和字幕改动。实施前重读状态与相关文件，围绕最终 UI 接入，避免覆盖其他工作。
- 直接播放明确跳过当前在线操作，用户后续主动恢复时已经过去的弹幕不会补发；想完整观看需自行回到开头。

验证使用受控延迟/失败 API 和本地视频样本，覆盖状态转换、缓存保存、双端桌面交互和全屏。Web 证据不代替 Electron 实测，未验证的表面明确记录。
