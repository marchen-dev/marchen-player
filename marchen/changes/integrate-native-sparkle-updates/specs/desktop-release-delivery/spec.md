## 目的

限定发布平台，保证最终安装包、更新源和迁移说明一致。

### 需求: 发布平台

发行流程 MUST 仅产出 macOS ARM64 和 Windows x64 客户端。

#### 场景: 发布平台验证

- **GIVEN** 执行客户端构建发布
- **WHEN** 收集安装包与更新元数据
- **THEN** 无 Linux 或 macOS x64 新包，文档说明 Apple Silicon 与最低系统要求
- **AND** 通用 Ubuntu CI 可保留；旧 Intel 客户端不得被引导安装 ARM64 包

### 需求: 完整且可运行的包

发行流程 MUST 在干净环境准备并检查最终包的媒体与更新资源。

#### 场景: 完整且可运行的包验证

- **GIVEN** 没有本地生成资源缓存
- **WHEN** 构建并检查 DMG、ZIP 或 Windows 安装产物
- **THEN** 媒体解码、字幕、音频资源及原生更新组件完整，资源/版本不符使检查失败
- **AND** macOS 最终应用完整性签名有效，不能用构建目录检查替代最终包检查

### 需求: 版本源与发布原子性

发布流程 MUST 校验版本号、正式渠道、公钥和签名，并在产物可用后才对正式客户端暴露更新。

#### 场景: 版本源与发布原子性验证

- **GIVEN** 准备发布新版本
- **WHEN** 校验 tag、包版本和更新元数据
- **THEN** 版本匹配、目标单调升级，测试/预发布不污染正式源，缺失密钥或占位公钥阻止发布
- **AND** 先上传验证产物再启用正式源；失败发布不宣称完成；密钥不进入客户端、仓库或日志

### 需求: 全量与直接差分

更新分发 SHALL 支持全量包和官方直接差分，首发或无适用差分时使用全量包。

#### 场景: 全量与直接差分验证

- **GIVEN** 客户端安装 A，发布 B
- **WHEN** 检查更新并下载
- **THEN** 有效差分可还原并验证 B，无差分时全量更新成功
- **AND** 差分失败遵循官方安全恢复机制，不安装未经验证产物；不要求多跳差分

### 需求: 迁移与发布说明

发布文档 SHALL 解释首次手动迁移、首次打开限制、旧记录不迁移和停止支持平台。

#### 场景: 迁移与发布说明验证

- **GIVEN** 旧版用户或新用户阅读下载页
- **WHEN** 选择安装或升级方式
- **THEN** 明确 ARM64 适用范围和手动覆盖步骤，不承诺旧签名客户端可直接自动升级
- **AND** 保留旧产物及历史记录，不自动删除远端发行；真实平台未验收必须标明

### 需求: 三渠道发行

发行流程 MUST 支持 X.Y.Z、X.Y.Z-alpha.N、X.Y.Z-beta.N。Alpha/Beta MUST 标记预发布，不设为 Latest；构建流程仅产出 draft，公开事件后才更新渠道。

#### 场景: 公开与渠道晋升

- **GIVEN** 完整发行已公开，当前有 stable、beta、alpha 客户端
- **WHEN** 发布正式版/Beta/Alpha
- **THEN** 分别进入三个渠道/两个预发布渠道/仅 Alpha，按最高语义版本选取
- **AND** Draft、无效版本、缺资产和错误校验不进入源；晚发布低版本不得使源回退，元数据更新失败保持原源
